# v3.0 Release Design: Devices, Momentary Buttons, and Retiring Old Behaviour

> **For Hermes:** This is a release design and research plan, not yet an implementation plan. Do not start coding from it. Task-level plans are written per workstream after the research checklist in §8 is complete and the owner has settled §9. This document authorizes no implementation, release, or live HA changes.

**Goal:** Bring the integration in line with current Home Assistant practice (one device per physical unit, event and button entities for keypad buttons, adding devices after setup) in a way that never breaks a user's setup without telling them first.

**Architecture:** Announce in one release, remove in a later one. v3.0 adds the new model next to the old and starts Home Assistant's standard deprecation notices. v4.0, at least six months later, removes what was deprecated. Nothing a user relies on stops working in the release that first tells them about it.

**Tech stack:** Python, Home Assistant entity/device/issue registries, config and options flows, existing serialx protocol, pytest-homeassistant-custom-component, Ruff.

**Status:** Draft, 2026-11-15. Baseline: main at b380380 (v2.0.2). Research done from documentation and tagged Home Assistant source only; nothing here has been run. Not reviewed.

**Tracking issues:** #40 per-device model, #41 button switch stays on, #42 add a device after setup, #43 status under a different device ID.

**Related plan:** `.hermes/plans/2026-11-04_163150-jetstream-devices.md` holds the detailed per-device design (identities, naming, areas, migration, triggers). This document sets the release sequence around it and adds the momentary-button design. Where the two disagree, this one is newer.

---

## 1. Principles

1. **No silent breaks.** Anything removed is deprecated first, with a Repairs notice inside Home Assistant that names what is affected.
2. **Group the pain.** Users should have one period of "things to update", not a trickle. Announcements land together in v3.0; removals land together in v4.0.
3. **Identities are stable.** Entity IDs and unique IDs of existing entities do not change in any release in this plan.
4. **Startup is never slowed.** No new serial traffic at startup beyond what v2.0.2 does.
5. **Elegance is not changed by v3.0** unless §9 decision D6 says otherwise.

## 2. What the research found

Sources are listed in §10. "Tagged source" means the Home Assistant Core 2026.11.0 tag.

### 2.1 Entity types for buttons

- Home Assistant's entity guidance is explicit. A physical push button that people press is an **event** entity. Something Home Assistant presses is a **button** entity. A **switch** is for things that stay on or off. A button entity "can't report presses that happen outside Home Assistant".
- So a JetStream keypad button needs two entities, not one "momentary switch": an event entity for presses at the wall, and a button entity to tap it from Home Assistant.
- Precedent in Core 2026.11: Lutron Caseta creates an event entity for every keypad and Pico button, has a separate outbound button platform, and still keeps its device triggers. Universal Devices ISY added event entities for Insteon buttons and keypads in 2026.10.

### 2.2 Standard press types are still changing

- Event entities with device class `button` can use standard event types so one automation works across integrations.
- Tagged source (2026.11.0) defines: `press_start`, `press_end`, `long_press_start`, `long_press_end`, `multi_press_ongoing`, `multi_press_end`.
- The development branch adds `single_press` and `multi_press`, and deprecates the two `multi_press_*` types for removal in 2027.5. The public docs already describe the development-branch set.
- Consequences: the right mapping for a JetStream "tap" (`single_press`) is not in 2026.11.0; and the docs forbid guessing ("only list a type if its meaning holds for every event you fire under that name", "do not synthesize events, and do not run timers"). Non-standard event types are allowed.
- JetStream sends three activity reports: tap (`T`), press (`P`), release (`R`). The manuals do not say what is sent for a hold or a double tap, or whether a tap also produces press and release. This needs the hardware test in §8.

### 2.3 How Home Assistant retires entities

From the Core "Deprecating" guide:

- "Anything you remove has to be deprecated first." Minimum period for user-facing things (entities, actions): **6 months**. It may be extended, never shortened.
- When an entity moves to another platform: "create the new entity first, and keep the old one working during the period."
- Raise a Repairs issue for every deprecated entity that still exists and is enabled. Use `automations_with_entity()` and `scripts_with_entity()` to name the automations and scripts that will break.
- The user acknowledges by disabling the old entity. Once it is disabled and unused, the integration removes it from the registry.
- An entity that does not exist yet is not created, so new users never get the deprecated entity.
- The issue is recreated on every start while the entity is in use; severity is WARNING while the old behaviour still works; include the config entry in the issue ID and set `config_entry_id`.

This guide is written for Core. HACS publishes no deprecation policy (its integration requirements page has none). Following the Core rule voluntarily is the proposal.

### 2.4 Device triggers

- Nothing found says device triggers are deprecated in general. Nanoleaf deprecated and then removed its touch-gesture device triggers in favour of an event entity (2026.11 release notes). Lutron Caseta kept its device triggers when adding event entities.
- Proposal: keep keypad device triggers through v3.x. Revisit for v4.0 with usage feedback.

### 2.5 Config subentries

- A subentry is a part of a config entry that users add, change and remove on its own, from the integration's page. Entities and devices can belong to a subentry and are removed with it. A config flow can create subentries at setup. The API exists in both 2026.5.0 and 2026.11.0.
- A device belongs to one config entry and at most one subentry (Core 2026.8). A device is moved with `async_update_device(new_config_subentry_id=...)`.
- `async_update_reload_and_abort` in a subentry reconfigure flow raises if the entry has an update listener. This integration has one (`__init__.py:68`).
- What this means here is in §5.

### 2.6 Device registry changes since the device plan was written

- `DeviceInfo["via_device"]`, `DeviceRegistry.async_get_device()` and `DeviceEntry.config_entries` are deprecated (removal 2027.8). Use `via_device_id`, `async_get_device_by_identifier(identifier, config_entry_id)` and `config_entry_id`. The device plan already uses `via_device_id`; recheck its other calls.

### 2.7 The two-ID report (#43)

- Both JetStream manuals define one Device ID per device, "the ID used to control this device using the JetStream Third Party Protocol", and show commands to `ddd` answered by `DEVdddll` for the same `ddd`. Neither describes status under a different ID.
- Two documented features would look like that from Home Assistant: a button programmed to control a **remote load** (another device's load), and **keypad emulation**, where a dimmer acts as a keypad and "the load can not be activated".
- Working conclusion: #43 is most likely how those two devices are programmed, not a protocol behaviour. Device identity stays one ID per device unless the reporter's data shows otherwise.

## 3. Release sequence

| Release | Contents | Breaks anything? |
|---|---|---|
| **v3.0** | Minimum HA raised to 2026.11. Per-device layout for new installs; opt-in for existing installs. Event and button entities for JetStream keypad buttons. Add and remove a device after setup. Button switches and the single-bridge layout marked deprecated, with Repairs notices. | Only for users on Home Assistant older than 2026.11, who stay on v2.0.x. |
| **v3.x** | Fixes and feedback. Notices keep appearing for anyone still on deprecated pieces. | No. |
| **v4.0** (no earlier than 6 months after v3.0) | Remove button switches that are disabled and unused; convert remaining single-bridge installs to per-device; decide on device triggers. | Yes, and every affected user has had an in-app notice naming their affected automations. |

Why not put the removals in v3.0: a user who updates through HACS would find switches gone and automations dead with no warning. That is the outcome the owner asked to avoid.

Why not ship the pieces as separate small releases: new entities should be created directly on the per-device layout, so they are named and placed once.

Minimum-version users: v2.0.x remains available in HACS. State in the v3.0 notes that v2.0.x gets no further features.

## 4. Keypad buttons (#41)

### 4.1 New entities

For each configured JetStream button (device, button 1 to 3):

- **Event entity**, device class `button`. Fires once per activity report from the bridge. Unique ID `{entry_id}_button_event_{device:03d}_{button:02d}`. Event types per §4.3.
- **Button entity**. Pressing it sends the existing tap command (`^T`). Unique ID `{entry_id}_button_press_{device:03d}_{button:02d}`.

Both attach to the unit device in per-device layout and to the bridge in the legacy layout, by the same rule as other entities.

Known limitation, unchanged: the bridge reports activity for taps sent by Home Assistant too, so the event entity also fires when the button entity is pressed. Document it. Confirm in §8 (H4).

### 4.2 Existing switches

- Keep class, unique ID, entity ID and behaviour exactly as in v2.0.2, including the stuck-on state. A deprecated entity is frozen; changing its behaviour now would be a second, unannounced change. (Alternative in §9, D3.)
- Mark deprecated using the Core pattern in §2.3: one Repairs issue per enabled switch, listing automations and scripts that use it, naming the two replacement entities, with `breaks_in_ha_version` omitted (that field is for Core versions) and the planned integration version stated in the text.
- Do not create button switches on new installs or for devices added after setup.
- Remove a switch from the registry once it is disabled and unused.

### 4.3 Event types (open until §8 H1 to H3)

Candidate mapping, to be confirmed or replaced by the hardware results:

| JetStream report | Candidate type | Depends on |
|---|---|---|
| `T` tap | `single_press` if the minimum HA version has it; otherwise an integration-specific `tap` | Which release first ships `single_press` (S2); whether a tap also sends `P`/`R` (H1) |
| `P` press | `press_start` only if it is sent when the button goes down on every press; `long_press_start` if it is only sent at the hold threshold | H2 |
| `R` release | `press_end` or `long_press_end` by the same test | H2 |
| double tap | none unless the bridge reports it distinctly | H3 |

Rule from the docs: when the hardware meaning is not certain, do not use a standard type for it.

### 4.4 Tests to write (when implementing)

Each new entity exists per configured button; an `ACT` line fires exactly one event of the mapped type; the button entity sends `^T`; the legacy switch is unchanged; a new install has no button switches; the Repairs issue appears for an enabled switch, lists a referencing automation, and disappears when the switch is disabled; a disabled, unused switch is removed and not recreated.

## 5. Devices and adding a device (#40, #42)

The detailed design is in the device plan. Decisions this document adds:

### 5.1 Stored lists stay; no subentries in v3.0

Considered: making every JetStream device a config subentry, which would give native Add, Change and Remove buttons on the integration page.

Not proposed for v3.0, because:

- Entities and devices belong to a subentry. Converting existing installs would move their entities onto per-device devices at upgrade, for everyone, with no consent step. That is exactly the silent change (bridge-targeted actions, inherited areas) the device plan's opt-in exists to prevent.
- Keeping opt-in would mean two storage models during the deprecation window: lists for unconverted installs, subentries for converted ones.
- The entry's update listener must go before subentry reconfigure can reload the entry.
- Whether Core relinks an existing entity row to a subentry without recreating it is unverified.

So: add and remove a device through the Configure menu, writing to the existing ID lists, as in the device plan §6A. Revisit subentries for v4.0, when every install is per-device and one storage model can be converted once.

### 5.2 Single-bridge layout is deprecated, not permanent

The device plan left the old layout available forever, so every later feature needed testing in two modes. Change: in v3.0 the old layout is deprecated. Existing installs get a Repairs notice describing the reorganisation, with the list of automations and scripts that target the bridge device (`automations_with_device`, `scripts_with_device`), and a link to opt in from Configure. v4.0 converts whoever has not.

The v4.0 automatic conversion must apply the same area and label rules as the opt-in path, without the per-case choices. Design that fallback before v3.0 ships, so the v3.0 notice can describe it truthfully.

### 5.3 Add and remove a device

As device plan §6A. One change: because button switches are deprecated, a device added after setup gets event and button entities only.

## 6. Smaller changes to fold into v3.0

Invisible to users unless noted:

- Rename the config flow step `import` to `devices` (the name `import` is reserved for YAML import).
- Replace deprecated device registry calls (§2.6).
- Add `config_entry_id` to the existing duplicate-ID and v1-migration Repairs issues so they are removed with the entry.
- README: an "Upgrading to v3" section, plus the event/button usage and the deprecation timeline. Visible.

Not proposed: changing unique-ID formats, moving scenes off the switch platform (JetStream scenes report on and off, so a switch fits), any Elegance entity change.

## 7. Risks

- **Six months is a long window to carry two models.** Accepted; it is the cost of principle 1. Keep the legacy paths frozen so they need no new work.
- **Standard press types change again before v3.0.** Pin the mapping to the minimum version at release time; prefer an integration-specific type over a standard one that might be redefined.
- **Users never open Repairs.** Also state the timeline in release notes and the README. Nothing more can be done from inside a custom integration.
- **The v4.0 automatic conversion surprises someone who ignored the notice.** Mitigated by the notice naming their affected automations for six months; residual risk accepted.
- **Hardware results contradict the candidate mapping.** Expected; §4.3 is provisional by design.

### Needs the owner's hardware (do together)

Setup for all H steps: debug logging on for `custom_components.centralite`; note the wall-clock time of each action; download the full log afterwards. Use one dimmer keypad with at least one button controlling its own load. No integration changes are needed for these.

| # | Do this | Record | Decides |
